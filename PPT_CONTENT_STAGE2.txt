SLIDE 6: MATHEMATICAL MODEL (Updated)
================================================================================

MODEL 1: SEMANTIC SIMILARITY FOR EXAMPLE RETRIEVAL
--------------------------------------------------

Embedding Generation:
    q_emb = SentenceTransformer(query)
    e_emb[i] = SentenceTransformer(example_i)

Cosine Similarity:
    sim_i = (q_emb . e_emb[i]) / (||q_emb|| x ||e_emb[i]||)

Top-K Selection:
    Selected = argmax_k(sim_i) for i in {1, ..., n}


MODEL 2: MULTI-TENANT QUERY FILTERING
-------------------------------------

Let Q be the generated SQL query. The system enforces:
    Q' = Q AND (organization_id = theta)

Where theta is the authenticated user's organization ID from JWT token.


MODEL 3: VALIDATION RETRY LOGIC
-------------------------------

for attempt in [0, max_retries]:
    SQL = Agent3.generate(prompt, feedback)
    valid, errors = Agent4.validate(SQL)
    if valid:
        return execute(SQL)
    feedback = errors
return Error("Max retries exceeded")


MODEL 4: CHART TYPE SELECTION FUNCTION
--------------------------------------

ChartType(data, intent) =
    | "line"  if has_temporal_dimension(data)
    | "pie"   if intent.type == "composition" AND |categories| <= 5
    | "bar"   otherwise

CORE FEATURES TABLE:
--------------------------------------------------------------------------------
| Feature                  | Description                      | Technology           |
|--------------------------|----------------------------------|----------------------|
| Natural Language Queries | Ask questions in plain English   | GPT-4o-mini+LangChain|
| 6-Agent Pipeline         | Specialized agents for each task | LangGraph            |
| RAG-Enhanced SQL         | Few-shot via semantic search     | ChromaDB+Transformers|
| Self-Correcting Valid.   | Retry loop for invalid SQL       | Agent 4 feedback     |
| Multi-Tenant Isolation   | Organization-based separation    | JWT + WHERE clause   |
| Auto-Visualization       | Intelligent chart selection      | Agent 6 logic        |
| Business Insights        | Actionable analytics summaries   | GPT-4o-mini analysis |
--------------------------------------------------------------------------------

ALGORITHM: 6-AGENT PIPELINE FLOW
--------------------------------

1. UNDERSTANDING AGENT
   Input: Natural language question
   Process: Extract intent, metrics, filters, groupings
   Output: Structured intent JSON

2. SCHEMA AGENT
   Input: Intent JSON
   Process: Map intent to tables, determine JOINs
   Output: Schema navigation plan

3. SQL GENERATION AGENT
   Input: Intent + Schema + RAG Examples
   Process: Construct SQL with few-shot prompting
   Output: SQL query with {org_id} placeholder

4. VALIDATION AGENT
   Input: Generated SQL
   Process: Syntax check, security scan, multi-tenant verification
   Output: Valid SQL or error feedback for retry

5. INSIGHTS AGENT
   Input: Query results
   Process: Statistical analysis + LLM interpretation
   Output: Summary, key insights, trends, anomalies

6. VISUALIZATION AGENT
   Input: Results + Intent
   Process: Determine chart type, configure axes
   Output: Chart configuration JSON

MULTI-TENANT STRUCTURE EXPLANATION:
-----------------------------------

Current Architecture (Shared Database):

+-------------------------------------------------------------+
|                    PostgreSQL Database                       |
+-------------------------------------------------------------+
|  Organization A (org_id=1)  |  Organization B (org_id=2)    |
|  ---------------------------|------------------------------ |
|  general_ledger (filtered)  |  general_ledger (filtered)    |
|  chart_of_accounts          |  chart_of_accounts            |
|  territory                  |  territory                    |
|  users                      |  users                        |
+-------------------------------------------------------------+

ISOLATION MECHANISM:
1. Every table (except calendar) has organization_id column
2. JWT token contains user's organization_id
3. Middleware extracts org_id and injects into all queries
4. All JOINs must include org_id matching:

   JOIN chart_of_accounts coa ON
       gl.organization_id = coa.organization_id AND
       gl.account_key = coa.account_key


SCALING STRATEGIES:
-----------------------------------
| Strategy              | Description                           | When to Use          |
|-----------------------|---------------------------------------|----------------------|
| Vertical Scaling      | Increase PostgreSQL resources         | < 100 organizations  |
| Read Replicas         | Separate read/write workloads         | High read volume     |
| Table Partitioning    | Partition by organization_id          | 100-1000 orgs        |
| Schema-per-Tenant     | Separate schema per org               | Need strong isolation|
| Database-per-Tenant   | Dedicated database per org            | Enterprise/compliance|
| Sharding              | Distribute across multiple DB servers | > 1000 orgs          |

RECOMMENDED SCALING PATH:

Stage 1: Shared DB + Row-level filtering (Current)
    |
    v (>50 orgs)
Stage 2: Add Read Replicas + Connection Pooling
    |
    v (>200 orgs)
Stage 3: Partition tables by organization_id
    |
    v (>1000 orgs or compliance needs)
Stage 4: Schema-per-Tenant or Database-per-Tenant
